A payment not observed at extraction time is not necessarily an unpaid invoice. The old report filled missing payment dates with the cutoff date, which made the youngest cohort appear better than it was. For the comparison below, I only score invoices with enough observation time for the target horizon. The remaining rows stay in a separate pending count.

Build each fold from a fixed extraction snapshot. Derive invoice-age features using that snapshot's available columns; do not let a later collection date reach feature preparation. Keep tenant salt fixed so reruns compare the same holdout. The input SQL writes a snapshot id into the Python training manifest. If that id is absent, stop before fitting rather than selecting the newest table.

The January replay changed the ranking of two candidate models. Aggregate error improved for one model while the small-tenant cohort became worse. We kept the previous model for that cohort and retained both reports. Deployment approval includes the cohort table, not just the average error.

2026-06-19: checked the production monitor against a simulated seven-day label delay. It generated a pending-label warning rather than a drift page. The scorer still runs on AWS; the old GCP batch job is not part of this path. Operations used the attached replay steps on 2026-06-17 and reproduced the pending counts from the stored manifest. Do not compare a newly matured cohort directly with last week's incomplete one.
