The May rollout stopped at node drain because the only remaining replica was protected by its disruption budget. The API was still serving traffic. Repeating drain did not help and force deletion would have turned a maintenance delay into an outage. We added temporary capacity, checked that the replacement pod became ready and only then continued the drain.

Before starting a pool change, list the disruption budgets and compare allowed disruptions with the planned drain batch. Check the autoscaler limits and the actual free capacity in the target zone. A node count in the Terraform plan says little about whether pods can schedule: affinity, requests and volume zone constraints still apply. Keep the plan and current pod placement in the change ticket.

If the rollout stalls, pause the pipeline before changing limits manually. Capture deployment status, pending pod events and the budget status. Use a temporary capacity change with a ticket reference, then reconcile it back into Terraform after recovery. Never edit the state just to silence a plan difference. Confirm that there is no running apply before recovering a stale lock.

On 2026-06-10 the secondary on-call followed this procedure in staging with a single-replica test deployment. The capacity preflight caught the blocked case, and the rollout completed after adding one node. We kept the old alert until that drill was finished. This page covers the drain sequence; operator code changes still go through the operator maintainers.
