# JMeter to k6 - what we moved and why

We moved the PR-time smoke and the release gate scenarios to k6 (JS). JMeter stays for the recon batch and the 8h soak because the JDBC samplers and the existing listeners are already there.

## Why k6 for gate tests
- Test code is plain JS in git, reviewable in a PR. .jmx diffs are not.
- Thresholds are first class: `http_req_duration: ['p(95)<450']` fails the run, exit code goes straight to GHA.
- One binary, small container, 200 VUs on a 2 vCPU runner is fine.

## What did not move
- JDBC and JMS load. k6 has no built-in JDBC.
- Anything needing the old BeanShell correlation helpers, until rewritten.

## Pattern we use
Scenario per flow with `ramping-arrival-rate` executor; `setup()` creates a token pool, scenarios borrow from a SharedArray. Metrics go to InfluxDB through `--out influxdb`, dashboard `k6-gate` in Grafana.

## Gotchas
- `check()` does not fail the run, `thresholds` do. Easy to miss.
- Do not log per-request in load runs, it dominates the CPU.
- Use `tags: { flow: 'invoice_create' }` so thresholds can be per flow.
