# Performance test strategy - billing-core and recon-engine

## Scope
Release-gating load tests for the invoice create/list/pay APIs (billing-core) and the nightly recon batch (recon-engine). Not covered: web-console rendering, mobile.

## Workload model
Production peak taken from the last 90 days of ingress logs: month-end day 1-3, 09:00-11:30 IST. Mix: 55% invoice list/search, 20% invoice create, 15% payment status poll, 10% export. Concurrency is derived with Little's law: users = throughput x (response time + think time). We pace with a constant-throughput timer; we do NOT open a fixed number of VUs and hope.

- Think time: 3-8 s uniform for UI-driven flows, 0 for pure API consumers (webhook senders).
- Data: 5,000 tenants from CSV, hot-tenant skew 20/80 to mimic the big customers. Cache warmness matters, run once cold, once warm, record both.

## Acceptance thresholds (current)
| Flow | p95 | p99 | error rate |
|---|---|---|---|
| invoice list | 450 ms | 900 ms | < 0.3% |
| invoice create | 700 ms | 1.4 s | < 0.2% |
| recon nightly batch | finish < 95 min for 2.1M rows | - | 0 |

Thresholds are compared against the last green baseline: a regression of more than 15% on p95 fails the release gate even when absolute numbers pass.

## Test types
Smoke (1 min, 5 users) per PR touching hot paths; load (30 min at peak); stress (step up until errors > 1%) monthly; soak (8 h at 60% peak) before major releases.

## Reading results
Look at percentiles not averages. Watch for coordinated omission when using closed-model tools; k6 arrival-rate executors and the JMeter throughput timer avoid most of it. Correlate with Grafana: app CPU, GC pause, DB connection pool wait, Kafka consumer lag. A bottleneck is claimed only with two signals pointing the same way.
